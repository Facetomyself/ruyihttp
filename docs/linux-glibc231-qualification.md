# Linux glibc 2.31 wheel qualification

The promotion gate runs on native `ubuntu-24.04` (`x86_64`) and `ubuntu-24.04-arm` (`aarch64`) hosted runners. The kernel is the runner's Linux kernel; the userland is Debian 11 Bullseye. Docker Official Python `3.10-bullseye` is pinned to a manifest index and one Linux manifest per architecture. There is no stable official `3.14-bullseye` image. The 3.14 endpoint builds the SHA-256-pinned CPython 3.14.10 source inside the same Bullseye manifest and copies only the installed interpreter prefix into a clean stage. The build extracts pinned, matching Bullseye libzstd headers for Python's standard-library `compression.zstd` extension; the original image supplies `libzstd.so.1` at runtime. The gate mounts neither host compiler or runtime libraries nor the product checkout. The offline test container has only its loopback network interface.

Each architecture and interpreter independently checks:

- Debian `libc6` and loaded glibc 2.31 (`getconf`, `confstr`, and `gnu_get_libc_version`), native machine architecture, interpreter loader paths, and system `libstdc++6` (Debian GCC 10). The wheel's versioned ELF **requirements**, not merely symbols it exports, must stay within `GLIBC_2.31`, `GLIBCXX_3.4.28`, and `CXXABI_1.3.12`. Loader output must resolve the runtime's glibc, libstdc++, and libgcc from the pinned distribution. Wheel sibling libraries must come from the installed package. The symbol ceilings are a Debian 11 qualification policy; a different distribution with glibc 2.31 can ship a different C++ runtime.
- Default pip compatibility tags include `py3-none-manylinux_2_31_<arch>` and exclude newer glibc tags. The exact public [`v0.9.3` Linux wheels](https://github.com/Facetomyself/ruyihttp/releases/tag/v0.9.3) at commit `e8f8b02703239a18a75760d791c15936af632c40` are rejected by normal pip with “not a supported wheel on this platform.” They are never installed on Bullseye.
- A fresh virtual environment installs the candidate by its exact filename without platform overrides or preinstalled dependency packages. PyPI wheels are required (no silent source builds). The pip report records the exact version, filename, and SHA-256 for every resolved wheel. Test fixtures are then installed separately. The MASQUE/SOCKS extra is resolved in another fresh virtual environment, without pinning or preinstalling a newer host-side dependency. The SHA-256 of the wheel selected by pip, the installed distribution's direct URL metadata, and the original artifact are compared.
- Strict installed-package identity, hashes for all 14 native libraries, and loopback HTTP/1.1, H2 and H3. The same wheel runs the official Firefox profile and H2 first-flight comparators, strict cert negatives, H3 body ABI and Alt-Svc tests (missing/skipped required tests fail), normal proxy-chain checks, and replay-safe request boundaries. Release qualification additionally requires the RFC 9298 MASQUE loopback wire receipt.

`probe` exercises the userland, exact old-wheel rejection, and a clean resolution and runtime smoke of the project dependencies. It has no candidate wheel and produces no promotion receipt. `candidate` accepts an explicitly versioned `0.9.4.dev…+gha.…` wheel only if it already has the real `manylinux_2_31` filename and internal tag. An uncombined native-source candidate can prove MASQUE dependency resolution, but its receipt explicitly separates that result from a wire test. `release` checks the exact `0.9.4` wheel and requires the wire test; it is the mode used before Linux wheel promotion.

The final Linux wheel job calls `bash ci/linux_floor/run.sh "$slot" wheelhouse native-evidence/glibc-2.31` before uploading its exact wheel directory. A separate [Linux floor workflow](../.github/workflows/linux-minimum.yml) consumes existing source or final artifacts by producing run ID, attempt, and kind. It never rebuilds or retags those wheels. The same workflow tests ordinary upgrades from the pinned public 0.9.3 wheels in *separate* native Ubuntu 24.04 jobs, where glibc 2.39 can run them.

Per-endpoint `summary.json` exists only after all required runtime gates finish and records the container identity, wheel SHA-256, native library hashes, dependency wheels, loader paths, and gates. The inline promotion gate publishes `both-endpoints.json` only after both receipts match each other and the exact bytes still in the upload directory. A failed job can still publish partial logs; those are diagnostic evidence rather than an acceptance receipt.
